# 가상 제품팀의 주간 보고 규칙

이 문서는 실습용 팀의 약속이다. 모든 회사가 사용하는 일반 규칙이라는 뜻은 아니다.

## 입력 필드

한 파일은 특정 주의 현황이다. `period_start`와 `report_date`는 보고 기간이며 날짜는 `YYYY-MM-DD` 형식이다. 보고 시점은 `report_date`의 하루가 아직 끝나지 않은 시점으로 본다. 컴퓨터의 오늘 날짜를 사용하지 않는다.

업무마다 `id`, `title`, `owner`, `status`, `due_date`, `deployed_at`, `verification`, `blocker`, `note`가 있다. `null`은 미기록이며 없는 값을 만들어 채우지 않는다. `verification`은 운영 환경 확인 결과로 `통과`, `실패`, `대기`, `미실시` 중 하나다. 개발 중 테스트와는 다르다.

## 분류 기준

각 업무를 **위험 → 완료 → 진행** 순서로 확인하여 한 범주에만 넣는다.

1. **위험**: 차단 요인(`blocker`)이 있거나, 배포했지만 운영 확인이 `통과`가 아니거나, 아직 완료 조건을 충족하지 못한 업무의 `due_date`가 `report_date`보다 이전이면 위험이다. 모순된 기록이나 판정에 필요한 필드가 없을 때도 위험으로 두고 확인할 사항을 적는다.
2. **완료**: `status`가 `배포 완료`이고, `deployed_at`이 보고 기준일 이내의 유효한 날짜이며, `verification`이 `통과`인 경우다. 개발 완료나 코드 병합만으로 완료 처리하지 않는다. 차단 요인이 남으면 앞의 위험 기준을 우선한다.
3. **진행**: 앞의 두 범주에 속하지 않은 업무다. 개발을 끝냈지만 배포 전인 일도 진행이다.

기한이 보고 기준일과 **같으면 지연이 아니다**. 완료된 업무는 과거 기한만 보고 현재 지연으로 분류하지 않는다. 날짜나 상태가 서로 맞지 않으면 임의로 고쳐 판정하지 않는다.

담당자가 없다는 사실 자체만으로 위험으로 바꾸지는 않는다. 담당자 칸에 `미정`을 적고 확인 항목에 남긴다. 일정 변경, 지연 원인, 새 담당자를 원문에 없는데 만들어 쓰지 않는다. 다음 행동 제안은 확정된 일정·약속과 구분한다.

## 보고서 형식

제목은 `팀명 주간 진행 보고서`로 쓰고 보고 기간과 기준일을 적는다.

- **요약**: 전체 업무 수와 완료·진행·위험 건수. 범주별 합계는 전체 수와 같아야 한다.
- **완료**: 업무 ID, 제목, 담당자, 완료를 판단한 배포일과 운영 확인 결과.
- **진행**: 업무 ID, 제목, 담당자, 현재 상태와 기한.
- **위험 및 확인 사항**: 업무 ID, 제목, 담당자, 위험 근거, 확인할 사항. 원인이 없으면 `원인 미기록`이라고 쓴다. 위험이 아닌 업무의 담당자 미정 등은 별도 확인 사항으로 표시할 수 있다.

각 범주 안에서는 업무 ID 순서로 정렬한다. 해당 범주에 업무가 없으면 `해당 없음`으로 표시한다. 원문의 모든 항목을 길게 복사하는 대신 분류 근거가 드러나게 쓴다.
